# TASK 2026-08-17 — Chronicle AI Studio 저장 구조 전면 교체 (기록장 방식)

## 배경

Chronicle AI Studio(`studio/`)의 대화가 **브라우저 안(localStorage)에만** 사실상 저장되고 있었다. 서버에는 인물 설정 파일(`data/personas_<username>.json`) 하나에 대화가 통째로 얹혀 함께 저장되는 구조였다.

미니PC 실데이터 실측(2026-08-17):

| 항목 | 실측값 |
|---|---|
| `personas_admin.json` 크기 | 3.2MB |
| 인물 수 | 11명 |
| 최장 대화 | 421턴 |
| 저장된 RAG 벡터 | **전 인물 0개** |
| `_temp_anonymous_*` 유령 항목 | 3개(341KB) |

이 구조의 문제는 세 층이었다.

1. **주인이 둘** — 화면이 전체 스냅샷을 보내고 서버가 무엇이 새것인지 되짚었다. 1판 구현의 검수 결함 8건이 전부 이 다리 안에서 나왔다.
2. **'덧붙이기'가 실제로는 통째 쓰기** — 말 한마디마다 3.2MB 파일 전체를 다시 썼다. N턴이면 O(N²).
3. **짝이 순서로만 묶임** — 턴과 벡터가 서로 다른 배열에서 위치로만 연결돼, 한 번 어긋나면 오류도 로그도 없이 영구히 밀렸다.

세 번째까지는 개별 수정으로 막을 수 있는 종류가 아니라고 판단해 **설계 자체를 갈아엎었다.**

## 새 저장 구조

```
data/users/<username>/
  characters/<charId>.json          인물 1명 = 파일 1개
  conversations/<convId>/
    turns.jsonl                     한 줄 = 한 턴   {"n":0,"t":{...}}
    vectors.jsonl                   한 줄 = 한 벡터 {"n":0,"v":[...]}
    meta.json                       제목·모드·호감도·기억메모·visibleTurns·updatedAt
```

목록 파일(`index.json`)은 두지 않는다 — 목록은 각 `meta.json`을 훑어 만든다. 별도 목록 파일은 본체와 어긋날 수 있는 두 번째 진실이 되기 때문이다.

### 핵심 규칙

- **현재 위치의 유일한 기준은 `meta.visibleTurns`** (기록장의 줄 수가 아니다).
  `n < visibleTurns` → 무시(재전송·중복 클릭) / `n = visibleTurns` → 이어쓰기 / `n > visibleTurns` → 400 거부.
  이 한 줄로 재전송 멱등 · 되돌린 뒤 이어쓰기 · 옛 화면의 뒷북 저장 방어가 모두 처리된다.
- **같은 `n`이 여러 줄이면 마지막 줄이 이긴다.** 되돌린 자리에 새로 쓴 턴이 옛 줄을 덮는다.
- **되돌리기는 삭제가 아니다** — `visibleTurns` 숫자만 줄인다. 취소 되돌리기(redo)가 공짜로 따라온다.
  redo 한도는 "가장 큰 번호"가 아니라 **"마지막 줄의 번호 + 1"** — 최대값 기준이면 버려진 갈래와 새 갈래를 이어붙인다.
- **벡터는 자리가 아니라 `n`으로 턴을 가리킨다.** 어긋남이 구조적으로 불가능해졌다.
- **쓰는 순서는 기록장 줄 → `meta.json`.** 그 사이에 죽으면 그 줄이 없는 셈이 되고 다음에 같은 번호가 덮는다(자가 치유).
- **쓰다 만 마지막 줄은 읽을 때 버린다.** 이어쓰기 전 파일 끝이 줄바꿈인지 확인한다.

**쓰기량 실측**: 421턴(기록장 387KB) 대화에 1턴 추가 → 실제로 쓴 양 **1,276바이트**. 배포본은 같은 상황에서 3.2MB를 다시 쓴다(약 2,500배 차이).

## 수정 내역

### 1. `studio/store.js` (신규) — 저장 담당

서버는 이 파일을 거쳐서만 디스크에 닿는다. 경로 안전 검사(`path.resolve` 접두 검사), 19금 판정 일원화(`isAdult19Character`), 원자적 쓰기(작은 파일 전용), 옛 데이터 이관을 모두 여기서 한다.

오류에 `code`(`INVALID`/`NOT_FOUND`/`CONFLICT`)를 붙여 던진다.

### 2. `studio/server.js` — 통로 교체

**지운 것**: 접두사 대조(`commonPrefixLength`) · 키 순서 무시 직렬화(`stableStringify`) · 인물에 대화를 얹어 돌려주던 `characterToPersonaEntry` · 마지막 턴을 다시 붙였다 잘라 메타만 갱신하던 꼼수 · **오류 문구를 글자로 대조해 상태코드를 정하던 `classifyStoreErrorStatus`**(문구를 다듬는 순간 조용히 500이 된다).

| 통로 | 하는 일 |
|---|---|
| `GET|POST /api/personas` | 인물 설정만. **`savedSession` 없음** — '주인이 둘'을 없애는 핵심 |
| `GET|POST /api/conversations` | 대화 목록 / 새 대화 |
| `POST /api/conversations/import` | 옛 데이터 한 방향 이사. 같은 `importKey`면 **409**, 덮어쓰기 동작 자체가 없음 |
| `GET /api/conversations/:id` | `meta` + `turns[]`. `?vectors=1`이면 벡터도 |
| `POST /api/conversations/:id/turns` | `{n, turn, vector?, meta?}`. 벡터 형식 검사를 턴 붙이기 **앞에** 둔다 |
| `POST /api/conversations/:id/vectors` | 늦게 도착한 벡터를 뒤늦게 붙이는 길 |
| `PATCH /api/conversations/:id` | `visibleTurns`가 되돌리기·취소 |
| `DELETE /api/conversations/:id` | 폴더째 |

`import`는 `:id` 경로보다 **먼저** 등록해 `'import'`가 대화 id로 읽히지 않게 했다.

### 3. `studio/app.js` · `index.html` · `style.css` — 화면 연결

- 말 한마디가 끝날 때마다 **그 한마디만** 번호를 붙여 보낸다. 500ms 뒤 전체를 밀어 넣던 경로는 인물 설정 저장용으로만 남았다.
- **소설 모드도 같은 통로를 쓴다** — 종전에는 서버 저장 경로가 아예 없어 계정을 바꾸면 원고가 사라졌다.
- 동기화 승자 규칙(`storyHistory`가 긴 쪽이 이긴다) **삭제**. 서버가 정본이고 견주지 않는다.
- 왼쪽 서랍에 **새 대화 시작 + 대화 목록**(제목·턴 수·현재 표시). 한 인물로 여러 대화.
- **취소 되돌리기 버튼 신설**(되살릴 게 없으면 숨김).
- 서버 저장이 실패하면 화면 구석에 경고를 남긴다(조용히 삼키지 않는다).
- 서버가 "번호에 구멍"이라며 거부하면 화면에 있는 것을 통째로 **새 대화(복구본)로 구조**한다. 서버 쪽은 안 건드리므로 잃는 게 없다.
- 벡터가 붙을 대화를 못 박았다 — 임베딩이 오는 사이 사용자가 다른 대화로 옮기면 남의 말에 벡터가 달린다.

### 4. RAG 복구 — **2026-01-14부터 죽어 있었다**

컨테이너 로그 실측: `models/text-embedding-004 is not found ... for embedContent` 404 반복. 구글이 그날 이 모델을 폐기했다. 실패가 `app.js`에서 `console.warn`으로 삼켜지고 `if (vector)`가 걸러내 **흔적이 남지 않았다.** 전 인물 벡터 0개의 원인이다.

- 모델을 **`gemini-embedding-001`**로 교체, `outputDimensionality: 768`을 함께 보낸다.
  차원 줄이기는 **`gemini-embedding` 계열에만** 싣는다 — 옛 모델에 넣으면 요청 자체가 튕긴다.
- 실패 사유와 모델 이름을 화면까지 올려 **"⚠ 기억 검색 꺼짐"**을 띄운다. 성공하면 사라진다.
- 대화를 열면 저장된 벡터가 되살아난다(`?vectors=1`, 같은 번호의 말에 붙인다). 벡터를 함께 받는 것은 **대화를 열 때뿐** — 매번 받으면 421턴×768차원이 수 MB로 오간다.
- **정규화는 필요 없다.** `cosineSimilarity`가 두 벡터 각각의 크기로 나누는 정통 코사인이라 크기에 결과가 불변이다(크기만 10배인 벡터가 같은 점수를 내는 것을 검사로 확인). 768을 쓰는 이유는 품질이 아니라 저장량(1/4).

### 5. `_temp_anonymous_*` 유령 — 원인과 처리

쓰기는 `selectPersonaPreset.value || "_temp_anonymous_" + charName`, 읽기는 `_temp_`를 보지 않았다. 프리셋을 고르지 않고 대화하면 **같은 대화가 두 갈래로 갈렸다.**

턴 수 실측 — 박민정 155 / temp **157**, 한지수 421 / temp 238, 소미 205 / temp 128. temp 쪽이 더 많은 경우가 있어 **지우면 안 된다.** 새 구조의 '인물당 여러 대화'를 이용해 `"<이름> (자동 저장본)"`이라는 별도 대화로 이사시킨다. 짝지을 인물이 없으면 그 키로 인물을 새로 만든다(대화만 남기면 화면에서 열 방법이 없다).

읽는 쪽과 쓰는 쪽의 키를 맞춰 **유령이 더 이상 생기지 않는다.**

### 검사가 잡아낸 실제 결함

`GET /api/conversations` 목록에 **`importKey`가 실려 있지 않았다.** 그래서 화면이 이미 옮긴 옛 대화를 찾지 못하고, 매번 다시 올리려다 409로 막히고, 결국 **대화를 하나도 열지 않은 상태**로 남았다. 그 상태에서 말을 하면 새 대화가 만들어지고 번호가 어긋나 세션마다 '복구본'이 쌓였을 것이다.

이 결함은 "대화 개수가 안 늘어난다"만 보던 검사를 **통과했다.** 검사에 "실제로 그 대화를 열고 있는지"를 추가했다.

## 확인하지 못한 것

- **진짜 구글 호출을 아직 안 해봤다.** 대역은 우리가 보내는 요청 모양만 확인해줄 뿐, `gemini-embedding-001`이 실제로 768개를 돌려주는지는 증명하지 못한다. API 열쇠가 서버에 없고 사용자가 브라우저에 넣는 값이라 이 머신에 없다. 실제 차원이 다르면 `EMBED_DIMENSIONS` 상수 하나만 바꾸면 된다(코사인이라 값이 달라도 동작은 한다).
- **jsdom은 진짜 브라우저가 아니다.** 화면 배치·CSS·실제 렌더링은 확인되지 않았다. playwright chromium을 설치했으나 시스템 라이브러리 4개(libnspr4·libnss3·libnssutil3·libasound2)가 없어 실행하지 못했다(설치에 sudo 필요).
- **19금 가리기 갈래는 실행되지 않는다** — `authMiddleware({adminOnly: true})`가 일반 계정을 그 앞에서 막기 때문이다. 관리자 토큰으로만 두드릴 수 있어 검사도 못 했다. 빗장을 풀 때 실측 검증해야 한다.
- **옛 데이터 이사(D단계)는 미니PC 실데이터로 확인해야 한다.** 이관 코드는 사용자 폴더를 만들 때 자동 실행되도록 들어가 있고 원본 `personas_<username>.json`은 지우지 않으므로 되돌릴 길은 남아 있다.

## 남은 한계 (다음 작업자가 알아야 할 것)

- `.migrated` 표식이 사라지면 재이관이 다시 돈다. 파괴적이지는 않으나(이미 있는 파일은 건너뜀) 사용자가 지운 '레거시 유래' 항목이 되살아난다.
- 프리셋 이름이 바뀐 뒤 재이관하면 옛 이름 파일이 고아로 남아 목록에 유령으로 뜬다(삭제 로직 없음).
- 대화 파일은 있는데 벡터만 빠진 어긋난 상태는 재이관으로 복구되지 않는다. 검색 품질 저하로 그치고 데이터 손상은 아니다.
- `express.json`의 `limit`이 10MB인데 옛 파일이 3.2MB였다 — 넘으면 413으로 조용히 죽고 사용자 알림이 없었다(`alert`은 401일 때만). 새 구조에서는 한 번에 보내는 양이 1KB대라 이 위험이 사라졌다.

## 설계 과정에서 배운 것

1판 구현에서 검수를 4회 돌리는 동안 **세 번 연속 "앞 결함을 고친 방식이 더 큰 결함을 만들었다."**

- `.migrated`가 사라지면 재이관하도록 고쳤더니 → 정상 운영 중에 사용자가 새로 만든 인물·대화를 **전멸**시켰다.
- 결정적 id로 바꿔 전멸은 막았더니 → 같은 id를 무조건 덮어써서 사용자가 그 뒤 수정한 설정이 **조용히 원상복구**됐다.

공통 원인은 **'실패 복구'를 위한 조치가 '정상 운영'까지 사정권에 넣은 것**이다. 복구 동작을 설계할 때는 그 동작이 평상시에도 켜질 수 있는 조건인지부터 따져야 한다.

그리고 8회의 검수 결함이 **전부 같은 자리**(화면의 통짜 스냅샷을 서버가 역추적하는 다리)에서 나왔다는 사실 자체가, 개별 수정이 아니라 설계를 바꿔야 한다는 신호였다.
