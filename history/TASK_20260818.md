# TASK 2026-08-18 — Chronicle AI Studio 수위(chatLevel) 소유권 정리

## 신고

"설정에서 수위를 바꿔도 대화에 들어가면 옛 수위로 되돌아간다."

## 처음 한 일 — 잘못 짚은 수정

웹에서 받아온 수정안을 그대로 반영해 배포했다(커밋 `eaabfcb`).
`savePersona()`에서 인물 설정을 저장할 때 `savedSession.chatLevel`도 함께 갈아끼우는 내용이었다.

**효과가 없었다.** 그 코드가 손대는 곳은 브라우저 안 옛 저장소(localStorage)의
`savedSession`이고, 지금 대화는 전부 서버 파일(`data/users/<u>/conversations/<id>/meta.json`)에서
온다. 증상이 나는 길을 아예 지나가지 않는 수정이었다.

증상만 보고 건네받은 수정을 반영했을 뿐, **원인을 끝까지 따라가지 않은 것이 잘못**이다.

## 실제 원인 — 수위의 주인이 셋이었다

같은 값이 세 곳에 살고 서로를 덮고 있었다.

| 자리 | 값 | 누가 이기나 |
|---|---|---|
| 인물 설정 (`characters/<id>.json`의 `level`) | 사용자가 설정창에서 바꾸는 값 | 대화를 열 때 먼저 얹힌다 |
| 대화 (`conversations/<id>/meta.json`의 `chatLevel`) | 대화를 만들 때 박힌 값 | **그 위에 덮어써서 최종 승자** |
| 브라우저 옛 세션 (`savedSession.chatLevel`) | 서버 이사 전 데이터 | 설정창 표시를 덮고 있었다 |

`applyConversationContext()`가 `applyCharacterOfConversation()`으로 인물 수위를 얹은 **직후**
`conv.chatLevel`로 다시 덮는다(app.js). 그래서 인물 설정을 무엇으로 바꿔도 대화에 박힌 값이 이긴다.

또한 `loadSelectedPersona()`는 설정창 표시값을 `savedSession.chatLevel` → `data.level` 순으로 골라,
**설정창 자체가 옛 대화 값을 보여주고** 있었다.

## 사용자 결정 — 역할을 가른다

- 설정창의 수위 = **그 인물의 기본값**
- 새 대화 = 기본값을 물려받는다
- 대화 중에는 **그 대화의 수위만** 바꾼다
- 대화를 다시 열면 그 대화에 저장된 수위

# 계정관리 2묶음 — 관리 화면 · 내 비밀번호 바꾸기 (2026-08-18)

설계: `history/DESIGN_ACCOUNTS_20260818.md` (4묶음 중 **2묶음**)

## 무엇이 생겼나

| 주소 | 무엇 |
|---|---|
| `/admin/accounts` | 계정 목록·만들기·권한 변경·잠그기/풀기·비밀번호 초기화·지우기 (관리자만) |
| `/account` | 본인 비밀번호 바꾸기 (관리자가 아니어도 쓴다) |

대문 위쪽에 두 화면으로 가는 링크를 붙였다(계정 관리는 관리자에게만 보인다).

## 핵심 판단 — 계정 관리만은 표를 직접 본다

출입증은 30일짜리라 그 안의 `is_admin`은 **발급 시점의 사실**일 뿐이다.
그것만 믿으면 이미 지워졌거나 잠긴 관리자가 계속 관리 화면을 쓴다.
`account_admin_required`가 매 요청마다 표에서 **살아 있는 관리자인지** 다시 본다.

같은 이유로 이 통로만은 `X-API-Key` 우회를 받지 않는다
(`login_required(admin_only=True, allow_api_key=False)`).
열쇠 하나로 계정 생성·권한 상승이 되는 길을 끊었다 — 배포 자동화가 쓰던 다른 통로는 그대로다.

## 안전장치

- 자기 자신은 잠그거나 지울 수 없고, 관리자 표시도 스스로 뗄 수 없다
- 마지막 관리자는 잠그거나 지울 수 없다
- **잠긴 관리자는 머릿수에 넣지 않는다** — 잠긴 사람은 들어올 수 없기 때문이다
- 지울 때 아이디를 직접 입력해야 진행한다

## 계정 지우기와 자료

| 곳 | 어떻게 되나 |
|---|---|
| 계정 | 지워진다 |
| Chronicle AI 인물·대화 | **체크칸, 기본 꺼짐**(사용자 확정). 켜면 폴더째 지운다 |
| 갤러리 파일 | **남는다** — 올린 사람 기록이 없어 골라낼 수 없다. 지우는 창에 그대로 적었다 |

스튜디오에 `DELETE /api/admin/user-data/:username`을 새로 냈다.
포털이 **스스로 만든 관리자 출입증**을 붙여 부른다(두 서비스가 같은 `SECRET_KEY`를 쓴다).
닿지 못하면 계정은 지우되 **못 지웠다는 사실을 화면에 그대로 알린다**(조용히 성공으로 넘기지 않는다).

## 아이디 글자 제한

`^[A-Za-z0-9_-]{2,32}$` — 스튜디오가 허용하는 것(`A-Za-z0-9_.@-`)보다 **좁게** 잡았다.
스튜디오가 아이디를 폴더 이름으로 쓰므로, 점과 @를 빼면 경로가 위로 올라가거나
폴더 자신을 가리키는 경우를 생각할 필요가 아예 없어진다.

도달하더라도 이제 public으로 되돌리지 않고 **거절한다.**

올리기 단추는 `is_admin` 안쪽에 있어 **허락받은 일반 계정에게 안 보였다.**

# 계정관리 4묶음 — Chronicle AI 빗장 해제 · 19금 열람 분리 (2026-08-18)

커밋 `38463ac`(코드) · `273feb7`(포털 첫 화면 바로가기)

## 무엇이 바뀌었나

`isAdmin` 한 값이 **두 뜻**을 겸하고 있었다 — (가) 스튜디오에 들어올 수 있는가 (나) 19금을 볼 수 있는가.
(가)를 없애고 (나)를 `canAdult`로 갈랐다. 관리자는 `canAdult`가 자동으로 참이다.

| 파일 | 전 | 후 |
|---|---|---|
| `server.js`·`store.js`·`app.js`의 `isAdmin` | 49줄 | **7줄** |
| `canAdult` | 0 | **51줄** |

남은 7줄은 관리용 통로 하나(`/api/admin/user-data/:username`)와 옛 화면 대비 예비뿐이다.

## 착수 전 재실측

설계서가 지시한 3자리를 다시 봤다. 컨테이너 안 코드와 내 컴퓨터 코드를 **글자 수까지 대조**했고,
옛 빗장(`adminOnly`)은 컨테이너에서 **0곳**이었다.

## 실측 — 이 갈래는 한 번도 실행된 적이 없었다

빗장 때문에 19금 가리기 코드는 배포 이래 한 번도 돌지 않았다. 시험용 계정(`t19test`)을
만들어 19금 인물 1명·보통 인물 1명·대화 3개를 넣고, 19금 허용을 끈 뒤 확인했다.

| 확인 | 결과 |
|---|---|
| 관리자 아닌 계정이 스튜디오에 들어가는가 | 들어감 |
| 19금 허용을 끄면 반영까지 | **10초** (3묶음의 1분 캐시 안) |
| 19금 인물이 목록에서 사라지는가 | 사라짐 |
| 19금 대화를 주소로 직접 두드리면 | **404** — 감춤과 없음이 구분되지 않음 |
| 감춰진 19금 자료가 저장으로 지워지는가 | 안 지워짐 (파일 그대로) |
| 19금 대화를 새로 만들려 하면 | 403 + 안내문 |
| 19금 인물을 새로 만들려 하면 | 조용히 걸러냄(성공으로 끝남) |

대화가 감춰지는 길은 두 갈래인데(**대화 자체가 19금** · **19금 인물에 붙은 보통 대화**)
둘 다 404였다. 설계서는 앞 갈래만 적었으나 뒤 갈래도 실측했다.

## 배포 뒤에 사용자가 잡은 것 — 문은 열렸는데 문패가 없었다

`guest0` 계정으로 로그인하니 **Chronicle AI 링크가 안 보였다.**
스튜디오 자체는 열려 있었다(시험 계정으로 실제 입장을 확인했다). 막힌 것은
`portal/templates/index.html`의 바로가기가 `{% if is_admin %}`에 감싸여 있던 것이었다.

**왜 놓쳤나** — 설계서의 "손대는 파일"에 포털 화면은 "화면 2장 신설"로만 적혀 있었고,
**이미 있던 첫 화면의 바로가기 조건은 목록에 없었다.** 구현에서도 스튜디오 파일만 봤다.
빗장을 서버에서 푸는 것과 문패를 다는 것이 서로 다른 파일에 살고 있었다.

같이 훑어본 결과 **같은 종류의 잔존은 이 한 곳뿐**이었다 — 갤러리는 3묶음에서 이미
올리기(`can_upload`)와 관리(`is_admin`)를 갈라놓았고, 포털의 나머지 관리자 조건은
전부 진짜 관리자용(관리자 표시·계정 관리 링크)이다.

# 🔴 갤러리 신분 유출 — 다른 사람 출입증으로 들어가지던 결함 (2026-08-18)

커밋 `1be84b8`

## 무슨 일이 있었나

사용자가 `guest0`(public 폴더만, 올리기 불가)을 만들었는데 **갤러리에서 전부 보인다**고 신고했다.
이어 `guest1`로 로그인한 브라우저의 화면을 보내왔다 — 갤러리 왼쪽 위에 **`admin`** 이 달려 있었고
`총 433개 파일`, private·family 표가 붙은 항목이 그대로 나왔다.

## 원인

계정 저장소도, 권한 통로도, 갤러리의 폴더 검사도 전부 정상이었다.
새는 곳은 **신분**이었다.

갤러리만 자기 전용 출입증 `gallery_auth_token`을 30일짜리로 따로 들고 있었다.

1. admin으로 갤러리를 한 번 열면 브라우저에 admin 표가 30일간 박힌다
2. 포털에서 로그아웃해도 **이 표는 안 지워진다** — 호스트 전용 쿠키라 `onnamu.kr` 쪽에서 못 지운다
3. guest1로 다시 로그인하면 공용 출입증만 바뀐다
4. 첫 화면의 갤러리 링크에는 새 출입증이 안 실려 있다
5. 갤러리는 자기 주머니 속 **admin 표**를 읽는다

계정관리 4묶음 내내 잰 것은 전부 **권한**(무엇을 볼 수 있나)이었고,
**신분**(정말 이 사람인가)은 한 번도 재지 않았다. 경중의 순서가 거꾸로였다.

## 고친 것

`gallery/auth_helper.py` — `gallery_auth_token`을 **신분에서 '베껴 둔 사본'으로 격하**했다.

| 상황 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 사본=admin, 지금 로그인=guest1 | admin으로 들어감 | **guest1로 들어가고 사본을 갈아 끼움** |
| 사본만 남고 로그아웃 상태 | admin으로 들어감 | **로그인 화면으로 보냄** |
| 손잡기 뒤에도 확인 불가 | — | **403 (무한 왕복 방지)** |
| 집 안 IP:포트 접속 | 사본 사용 | 종전대로 (공용 쿠키가 안 오는 구역) |

신분 판정을 **`current_identity()` 한 곳**으로 모았다.
`/upload_chunk`·`/upload_complete` 두 API가 `login_required`를 지나지 않고
쿠키를 직접 읽고 있었다 — **같은 사고의 두 번째 자리**였고 같이 고쳤다.
