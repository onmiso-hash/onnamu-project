# TASK 2026-08-16 — 영화관 첫 화면 성능 개선 (1단계)

## 배경

영화 편수가 늘면서 영화관(`/movies`) 첫 로딩이 느려지고 버벅거린다는 보고. 일반 갤러리(`/`)와 비교 분석한 결과, 원인은 영상 전송 경로가 아니라 **목록을 만드는 방식**에 있었다.

사용자가 기억한 예전 스트리밍 URL(`http://stream.onnamu.kr:50002/movies`)은 깃 이력에서 확인됨 — 2026-05-17 커밋 `46a8b0c`(미디어 서비스 통합)에서 제거되었고, 클라우드플레어 DNS에는 `stream.onnamu.kr` A 레코드(121.148.79.170, DNS 전용)가 아직 살아 있다. 다만 **당시 목록 화면이 지금보다 빨랐던 것은 아니며**(그때는 썸네일로 영상 파일 자체를 내려받았고, 06-21에 ffmpeg JPG로 전환한 것이 개선), 직행 경로는 재생 시 대역폭 문제이지 첫 화면 지연의 원인이 아니다. 영상 직행 경로 복원은 2단계로 분리했다.

## 진단

| 항목 | 일반 갤러리 | 영화관 (수정 전) |
|---|---|---|
| 페이지네이션 | 24개/쪽 | **없음 — 전량 렌더링** |
| 파일당 서버 작업 | 이름만 | 크기 + 자막 탐색(디렉터리 3회 스캔) |
| 동시 ffmpeg | 해당 없음 | **제한 없음** |

핵심은 `get_all_files()`가 영화 한 편마다 `find_subtitle()`을 호출하고, 그 안에서 자막 확장자 3종에 대해 `directory.glob()`을 도는 구조였다. 자막이 없는 영화는 매번 디렉터리를 끝까지 스캔한다 → **편수의 제곱에 비례**. 게다가 이렇게 찾은 `subtitle` 값은 `movies.html`·`manage.html` 어디에서도 사용되지 않는다(재생 화면 `player()`가 자체적으로 다시 호출).

## 수정 내역 (5건)

### 1. `get_all_files()` — 디렉터리 1회 스캔 (gallery/app.py)
- `Path.iterdir()` + 편당 `find_subtitle()` → `os.scandir()` 1회 후 이름 목록에서 매칭.
- 신규 `match_subtitle(subtitle_names, video_stem)` 추가. **`find_subtitle()`은 `player()`가 계속 쓰므로 유지.**
- 두 함수의 동작 동일성을 임시 디렉터리 대조 테스트로 검증 (정확 일치·언어 접미사·괄호/대괄호 포함 이름·빈 언어표시 등 10케이스 전부 일치).

### 2. `/movies` 페이지네이션 (gallery/app.py, movies.html)
- `gallery()`와 동일하게 `PER_PAGE = 24` 적용, 페이지 번호 클램프.
- `movies.html`에 `gallery.html`과 같은 모양의 페이지네이션 마크업·스타일 추가, 부제에 전체 편수 표기.

### 3. 썸네일 캐시 영속화 (gallery/docker-compose.yml)
- `/app/.thumbnails`가 컨테이너 내부에만 있어 `docker compose up --build` 때마다 전량 소실 → 재배포 후 첫 방문자가 전 영화 ffmpeg 비용을 혼자 부담.
- named volume `gallery_thumbnails` 추가.

### 4. ffmpeg 동시 실행 제한 (gallery/app.py)
- `THUMBNAIL_WORKERS = threading.Semaphore(2)`로 동시 2개 제한.
- 세마포어 획득 후 `thumb_path.exists()` 재확인 — 대기 중 다른 요청이 이미 생성한 경우 중복 작업 회피.
- 임시 파일명에 `threading.get_ident()` 추가 — Flask 개발 서버는 멀티스레드 단일 프로세스라 기존 pid suffix만으로는 같은 파일 동시 요청 시 충돌 가능(TASK_20260709의 "잔여 권장" 항목).

### 5. 미사용 `/stream` 라우트 제거 (gallery/app.py)
- 어느 템플릿도 참조하지 않음(`player.html`은 `/media/...` 사용).
- `Range: bytes=0-`(브라우저 기본) 요청 시 `f.read(length)`로 **영화 파일 전체를 메모리에 적재**하는 구조 → 삭제.
- 미사용이 된 `Response` import도 함께 제거.

## 검증

로컬 venv(flask 3.0.0)에 실제 앱을 올리고 가짜 미디어 트리(private 57편 + public 2편 = 59편, 자막 2종)로 테스트.

- `/movies` 1·2·3쪽 → 200, 카드 24·24·11개, 쪽 간 중복 없음. `page=99` → 3쪽으로 클램프.
- 자막 인식 2편 정확(`영화_03.ko.srt`, `영화_10.srt`), 전 항목 `size` 존재.
- `/`, `/?tab=images` → 200 (일반 갤러리 영향 없음).
- `/stream/...` → 404 (제거 확인).

**측정 (59편 기준, 목록 1회 생성)**

| | 디렉터리 스캔 | 항목 읽기 | 소요 |
|---|---:|---:|---:|
| 수정 전 | 172회 | 9,806회 | 28.0ms |
| 수정 후 | 2회 | 61회 | 0.4ms |

두 방식이 반환한 목록은 완전히 동일(`a == b` True).

> 이 수치는 개발 PC의 리눅스 디스크 기준이다. 실제 서버는 윈도우 디스크를 도커가 bind mount로 빌려 쓰는 구조라 항목 1회 읽기 비용이 훨씬 크므로 개선 폭은 이보다 클 것으로 보이나, **서버에서 직접 재지는 않았다.**
