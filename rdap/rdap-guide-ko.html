조회 버튼을 누르면 무슨 일이 일어나나요?

RDAP에는 전 세계 정보를 한곳에 모아 둔 중앙 서버가 없습니다. 도메인 정보는 각 레지스트리가, IP 주소 정보는 대륙별 인터넷 주소 관리기관(RIR)이 각자 자기 서버에 갖고 있지요. 그래서 조회가 두 번에 나뉘어 일어납니다.

  1. 어디에 물어볼지 찾기(부트스트랩). .com은 베리사인, 8.8.8.8은 ARIN이 맡고 있습니다. 입력하신 값을 어느 서버가 담당하는지 IANA가 펴내는 목록에서 찾아냅니다. 온나무 RDAP은 이 목록을 하루 한 번 받아 두고 씁니다.
  2. 담당 서버로 넘기기(리다이렉트). 찾아낸 주소로 HTTP 302 응답을 돌려보냅니다. 등록 정보 자체는 그 서버가 직접 만들어 보내 줍니다.

화면에 보이는 내용은 온나무가 가공한 것이 아니라 레지스트리가 그 순간 내려 준 원본 그대로입니다. 그래서 어떤 항목이 비어 있는 이유를 찾으려면 대개 그 레지스트리의 공개 정책을 봐야 합니다.

모든 응답에 공통으로 들어가는 것

무엇을 조회하든 응답의 뼈대는 같습니다. RFC 9083이 정해 놓은 모양입니다.

필드 무엇을 뜻하나
rdapConformance이 응답이 따르는 규격 목록입니다. 보통 rdap_level_0이 들어 있고, 확장을 쓰는 서버는 redacted 같은 이름을 덧붙입니다.
objectClassName이 묶음이 무엇인지 알려 줍니다. domain, nameserver, entity, ip network, autnum 가운데 하나가 옵니다.
handle레지스트리가 이 객체에 매긴 고유 번호입니다. 도메인이라면 2138514_DOMAIN_COM-VRSN 같은 모양이 됩니다.
links관련 주소를 모아 둔 곳입니다. rel: "self"는 이 객체 자신의 RDAP 주소이고, rel: "related"는 등록대행자 쪽 정보처럼 이어서 볼 만한 자료를 가리킵니다.
notices이용 조건이나 개인정보 고지처럼 서비스 전체에 붙는 안내입니다. 조회한 대상이 아니라 서버 쪽 이야기입니다.
remarks조회한 대상에 직접 달리는 비고입니다. "일부 항목은 개인정보 보호로 가렸다" 같은 문구가 여기 옵니다.
port43같은 정보를 옛 방식인 WHOIS로 받을 수 있는 서버 이름입니다. 아직 운영 중인 곳만 적혀 있습니다.
lang응답에 쓰인 언어입니다. 거의 en으로 옵니다.

도메인 응답 읽기

google.com을 조회하면 이런 응답이 돌아옵니다. 긴 부분은 덜어 냈습니다.

{
  "objectClassName": "domain",
  "handle": "2138514_DOMAIN_COM-VRSN",
  "ldhName": "GOOGLE.COM",
  "status": ["client delete prohibited", "client transfer prohibited"],
  "events": [
    { "eventAction": "registration",  "eventDate": "1997-09-15T04:00:00Z" },
    { "eventAction": "expiration",    "eventDate": "2028-09-14T04:00:00Z" },
    { "eventAction": "last changed",  "eventDate": "2019-09-09T15:39:04Z" }
  ],
  "nameservers": [ { "objectClassName": "nameserver", "ldhName": "NS1.GOOGLE.COM" } ],
  "entities": [ { "objectClassName": "entity", "roles": ["registrar"] } ],
  "secureDNS": { "delegationSigned": false }
}
필드 설명
ldhName영문자와 숫자, 붙임표로만 적은 이름입니다. 한글 도메인이라면 xn--로 시작하는 퓨니코드가 들어갑니다.
unicodeName사람이 읽는 원래 이름입니다. 한국.kr처럼 나오고, 영문 도메인에는 이 칸이 아예 없기도 합니다.
status지금 걸려 있는 잠금과 보류를 모아 둔 목록입니다. 값 하나하나는 아래 표에서 풀어 놓았습니다.
events등록하고 만료되고 바뀐 시각입니다. 끝에 Z가 붙은 UTC 표기라, 한국 시간으로 보려면 9시간을 더하면 됩니다.
entities사람과 회사 정보가 담깁니다. 등록자인지 관리 담당인지 기술 담당인지는 roles로 갈라집니다.
nameservers이 도메인의 주소를 실제로 답해 주는 DNS 서버입니다.
secureDNSDNSSEC 서명이 걸렸는지 알려 줍니다. delegationSigned가 true면 위조 방지 서명이 있다는 뜻입니다.

🔒 status 값 사전

status에 담기는 값은 도메인 등록 시스템(EPP)에서 쓰던 용어를 RDAP 표기로 옮긴 것입니다. 읽는 요령이 하나 있습니다. 앞에 client가 붙으면 등록대행자가 건 잠금이고, server가 붙으면 레지스트리가 건 잠금입니다. 뒤쪽이 더 무거운 잠금으로, 분쟁이나 법적 사유로 걸리는 경우가 많습니다.

값 뜻
active아무 제한 없이 정상적으로 쓰이고 있습니다.
client transfer prohibited다른 등록대행자로 옮기지 못하게 막아 둔 상태입니다. 도난을 막으려고 기본으로 걸어 두는 경우가 많아서, 이것만으로 문제가 있다고 볼 수는 없습니다.
client delete prohibited실수로 지워지지 않게 잠가 둔 상태입니다.
client update prohibited네임서버나 연락처를 고치지 못하게 잠가 둔 상태입니다.
client hold · server hold도메인이 DNS에서 빠져 접속 자체가 되지 않는 상태입니다. 요금 미납이나 신고, 분쟁 때문에 걸립니다.
pending transfer등록대행자를 옮기는 중입니다. 보통 닷새 안에 끝납니다.
pending delete삭제 절차의 마지막 단계입니다. 이 기간이 끝나면 누구나 등록할 수 있게 풀립니다.
redemption period만료 뒤에 주어지는 유예 기간입니다. 원래 주인이 비용을 더 내고 되살릴 수 있는 마지막 기회입니다.
add period · renew period막 등록했거나 연장한 직후의 기간입니다. 이 동안 취소하면 환불해 주는 규정이 있습니다.
inactive네임서버를 지정하지 않아 도메인이 동작하지 않습니다.
validated · pending validation연락처 확인 절차를 마쳤는지 보여 줍니다. 확인을 놓치면 도메인이 정지되기도 합니다.
associated주로 연락처에 붙는 값으로, 어딘가에 연결되어 쓰이고 있다는 뜻입니다.

날짜는 어떻게 읽나요

항목마다 무슨 일이 있었는지(eventAction)와 언제 있었는지(eventDate)가 짝을 이룹니다. 시각은 2028-09-14T04:00:00Z처럼 UTC로 적히니, 한국 시간으로 읽으려면 9시간을 더하세요.

eventAction 뜻
registration처음 등록한 시각입니다. 도메인이 얼마나 오래됐는지 여기서 알 수 있습니다.
expiration지금 등록 기간이 끝나는 시각입니다. 이날 바로 삭제되지는 않고 유예 기간이 이어집니다.
last changed등록 정보를 마지막으로 고친 시각입니다. 네임서버를 바꾸거나 기간을 연장했을 때 갱신됩니다.
transfer등록대행자가 바뀐 시각입니다.
last update of RDAP database이 응답을 만들어 낸 데이터베이스가 갱신된 시각입니다. 도메인이 바뀐 때가 아니라 자료를 새로 올린 때라 헷갈리기 쉽습니다.
deletion · reinstantiation삭제된 시각과 되살아난 시각입니다.

사람과 회사 정보는 entities에

연락처는 entities 배열에 들어갑니다. 각 항목에 붙은 roles를 보면 누구인지 알 수 있습니다.

  • registrant : 도메인의 실제 주인
  • administrative : 운영과 계약을 맡은 관리 담당
  • technical : 네임서버처럼 기술적인 문제를 처리하는 담당
  • billing : 결제 담당
  • registrar : 등록을 대행한 업체. 가비아나 GoDaddy 같은 곳입니다
  • reseller : 등록대행자의 재판매 업체
  • abuse : 스팸이나 침해 신고를 받는 창구입니다. 신고할 곳을 찾고 계신다면 여기를 보시면 됩니다
  • sponsor, noc : 후원 주체와 망 운영 센터입니다. 주로 IP나 ASN을 조회할 때 나옵니다

vcardArray가 왜 이렇게 생겼나요?

이름과 주소, 전화번호는 vcardArray라는 전자 명함(jCard) 형식에 담깁니다. 처음 보면 괄호가 겹겹이라 당황스럽지만 규칙은 간단합니다. [항목 이름, 부가정보, 자료형, 값] 이렇게 네 칸짜리 줄이 죽 이어질 뿐입니다.

["vcard", [
  ["version", {}, "text", "4.0"],
  ["fn",      {}, "text", "Google LLC"],
  ["adr",     { "cc": "US" }, "text", ["", "", "", "Mountain View", "CA", "94043", "US"]],
  ["email",   {}, "text", "abuse@example.com"],
  ["tel",     { "type": "voice" }, "uri", "tel:+1.6502530000"]
]]

fn은 표시 이름, org는 소속입니다. adr에는 사서함, 상세주소, 동네, 시, 도, 우편번호, 국가가 순서대로 들어가고 kind는 개인인지 단체인지를 알려 줍니다. 온나무 웹 클라이언트는 이 배열을 읽기 좋은 표로 바꿔서 보여 줍니다.

네임서버와 DNSSEC

네임서버 항목에는 이름(ldhName)만 있을 때도 있고 ipAddresses가 함께 붙을 때도 있습니다. v4와 v6로 나뉘어 있는 이 주소를 글루 레코드라고 부릅니다. ns1.google.com이 google.com을 담당하는 경우처럼 네임서버가 자기 도메인 안에 있으면 주소를 물어볼 곳이 없어지는데, 글루 레코드가 그 고리를 끊어 줍니다.

secureDNS에는 DNSSEC 설정이 담깁니다.

  • delegationSigned : 위조 방지 서명이 걸려 있는지 알려 줍니다. false라면 DNSSEC를 쓰지 않는 도메인입니다.
  • dsData : 서명 지문입니다. 열쇠 번호(keyTag), 서명 방식 번호(algorithm), 요약 방식(digestType), 지문 값(digest)으로 이뤄집니다.
  • maxSigLife : 서명의 최대 유효 기간을 초로 적습니다. 비어 있는 경우가 더 많습니다.

IP 주소와 AS 번호 응답

IP를 조회하면 그 주소 하나만이 아니라 주소가 속한 대역 전체의 정보가 돌아옵니다.

필드 설명
startAddress · endAddress할당된 대역의 첫 주소와 끝 주소입니다.
ipVersionv4 아니면 v6가 옵니다.
name대역에 붙은 이름표입니다. GOGL 같은 값이 들어가는데, 누가 쓰는 대역인지 짐작하는 실마리가 됩니다.
type배정 방식입니다. DIRECT ALLOCATION이나 ASSIGNED PA 같은 값으로, 기관이 직접 받은 대역인지 상위에서 나눠 받은 대역인지 구분합니다.
country등록된 국가 코드입니다. 서류상의 국가일 뿐이어서 실제 서버가 놓인 나라와는 다를 수 있습니다.
parentHandle이 대역을 나눠 준 상위 대역의 번호입니다.
cidr0_cidrs같은 대역을 8.8.8.0/24 같은 CIDR 표기로 다시 적어 주는 확장 항목입니다.
startAutnum · endAutnumAS 번호를 조회했을 때 나오는 값으로, 배정된 번호 구간을 뜻합니다.

AS 번호는 인터넷에서 경로를 광고하는 조직마다 붙는 번호입니다. 15169가 구글, 3356이 루멘의 번호입니다.

왜 등록자 이름이 안 보이나요

예전 WHOIS는 개인의 이름과 주소, 전화번호를 그대로 공개했습니다. 2018년 유럽 개인정보보호법(GDPR)이 시행된 뒤로는 개인 등록자의 정보를 가려 두는 쪽이 표준이 됐습니다. 그래서 응답에서 이런 모습을 자주 만나게 됩니다.

  • 값이 있어야 할 자리에 REDACTED FOR PRIVACY나 DATA REDACTED 같은 문구가 들어 있습니다
  • 이메일 대신 https://로 시작하는 문의 양식 주소가 들어 있습니다
  • redacted 확장(RFC 9537)을 쓰는 서버라면 어떤 항목을 왜 가렸는지까지 따로 적어 줍니다

회사나 기관 명의로 등록된 도메인은 개인정보가 아니라서 그대로 보이는 경우가 많습니다. 법 집행기관이나 지식재산권자처럼 정당한 사유가 있는 쪽에는 레지스트리가 별도 절차를 거쳐 정보를 내줍니다. RDAP이 WHOIS와 달리 요청자에 따라 응답을 달리 줄 수 있게 설계된 까닭이 여기에 있습니다.

결과가 안 나올 때

RDAP은 오류가 났을 때도 정해진 모양의 JSON을 돌려줍니다.

{
  "errorCode": 404,
  "title": "Not Found",
  "description": ["The requested object does not exist."]
}
  • 404 : 등록된 적이 없거나, 그 서버가 해당 자료를 갖고 있지 않습니다. 아직 아무도 등록하지 않은 도메인일 때가 가장 많습니다.
  • 400, 422 : 입력 형식이 규격에 맞지 않습니다. 공백이나 http://가 섞여 들어가지 않았는지 확인해 보세요.
  • 429 : 짧은 시간에 너무 많이 물어봤습니다. 잠시 뒤에 다시 해 보세요.
  • 501 : 그 레지스트리가 해당 조회 종류를 지원하지 않습니다.
  • 503 : 담당 레지스트리 서버가 점검 중이거나 응답하지 않습니다. 온나무 쪽이 아니라 상대 서버 사정인 경우가 대부분입니다.
  • 아무 응답도 없음 : 그 TLD가 아직 RDAP 서버를 운영하지 않습니다. 일부 국가 도메인이 여기에 해당합니다.

자주 헷갈리는 것들

  1. 만료일과 등록 가능일은 다릅니다. expiration이 지나도 유예 기간(redemption period, pending delete)이 보통 한 달 넘게 이어집니다. 그 도메인을 노리고 계시다면 이 기간이 모두 끝나야 합니다.
  2. client ~ prohibited는 경고가 아닙니다. 대부분의 등록대행자가 도난을 막으려고 기본으로 걸어 두는 잠금입니다.
  3. country는 서버 위치가 아닙니다. IP 대역에 적힌 국가는 등록 서류에 적힌 나라일 뿐, 장비는 다른 나라에 있을 수 있습니다.
